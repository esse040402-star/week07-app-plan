# 개인 앱 제안서

앱 이름: 나중에 노트 (LaterNote)
작성·수정 날짜: 2026-11-02 (초안 작성)

이 문서는 구현 전 기획 문서입니다. 앱 코드·실행 결과·사용자 조사 결과는 아직 없습니다.

## 1. 문제·사용자·핵심 가치

- 첫 사용자와 사용 순간: 수업·이동·대화 중에 "이건 나중에 해야지" 하고 떠올린 일을 그 자리에서 처리할 수 없는 대학생(작성자 본인). 사용 순간은 일이 떠오른 직후 10초 안팎의 짧은 틈이다.
- 현재 해결 방법과 불편: 머릿속으로만 기억하거나 카카오톡 나에게 보내기·메모 앱에 아무렇게나 적는다. 적은 위치가 흩어지고, 적은 뒤 다시 열어 보지 않아 결국 해야 할 때를 놓친다.
- 확인한 사실: 작성자 본인이 "나중에 해야겠다고 한 일을 까먹는" 경험이 있다고 밝혔다(본인 진술). 다른 사람의 경험·빈도·현재 방법은 조사하지 않았다.
- 아직 확인할 가설과 질문:
  - 가설 1: 잊는 이유는 적지 않아서가 아니라 "적은 뒤 다시 볼 때"가 정해져 있지 않아서이다.
    → 질문: "나중에 하려고 적어 둔 일을 마지막으로 다시 확인한 때는 언제인가?"
  - 가설 2: 떠오른 순간에는 정확한 날짜·시각보다 "오늘 저녁 / 내일 / 이번 주말" 정도로만 고를 수 있다.
    → 질문: "나중에 할 일을 적을 때 날짜까지 정해서 적는가?"
  - 가설 3: 알림이 없어도 앱을 열었을 때 "지금 할 것"만 모아 보여 주면 도움이 된다. (알림 필요성은 아직 모름)
    → 질문: "알림 없이 하루에 한 번 앱을 열어 확인할 수 있는가?"
- 앱 사용 후 얻을 핵심 도움: 떠오른 일을 짧게 적고 "다시 볼 때"를 고르면, 그때가 된 일만 한곳에서 다시 확인할 수 있다. (측정한 효과가 아니라 기대 변화)
- 사용자 스토리: 할 일이 갑자기 떠오른 대학생이 그 일을 짧게 적고 다시 볼 때를 골라 두어서, 그때가 되었을 때 잊지 않고 처리하고 싶다.

## 2. MVP와 범위

| 기능 | 필수·보류·제외 | 이유 |
| --- | --- | --- |
| 할 일 내용 입력·저장 | 필수 | 떠오른 일을 잃지 않게 붙잡는 첫 행동 |
| 다시 볼 때 선택(오늘 저녁·내일·이번 주말) | 필수 | 이 앱이 일반 메모와 다른 점. 없으면 "적고 안 보는" 문제가 그대로 남음 |
| "지금 볼 것" 목록과 "나중에" 목록 구분 | 필수 | 다시 볼 때가 된 일만 모아 보는 핵심 가치의 확인 수단 |
| 처리 완료 표시 | 필수 | 처리한 일을 "지금 볼 것"에서 빼야 남은 일이 보임 |
| 앱을 다시 열어도 기록 유지(기기 저장) | 필수 | 잊는 문제를 다루는 앱이라 재시작하면 사라지는 기록으로는 가치 확인 불가 (3장 결정 참고) |
| 정확한 날짜·시각 직접 지정 | 보류 | 가설 2 확인 전. 세 가지 선택지로 먼저 흐름 확인 |
| 푸시·로컬 알림 | 보류 | 가설 3 확인 전. 권한·플랫폼별 설정·새 패키지가 필요해 첫 흐름보다 범위가 큼 |
| 항목 수정·미루기("다음에 다시") | 보류 | 핵심 흐름 확인 뒤 사용 상황을 보고 결정 |
| 검색·태그 | 보류 | 항목이 쌓인 뒤에야 필요성이 생김 |
| 로그인·서버 동기화·여러 기기 | 제외 | 개인 1인·1기기 MVP이며 계정·서버 제외 제약과 충돌 |
| AI 자동 분류·음성 입력 | 제외 | 불편 해결에 꼭 필요한지 근거가 없고 유료 API 제외 제약과 충돌 |
| 친구와 할 일 공유 | 제외 | 개인 기록 목표에서 사용자·데이터 범위를 넓힘 |

필수 기능만으로 "떠올림 → 적고 시점 선택 → 그때 다시 확인 → 처리" 흐름이 처음부터 끝까지 이어지는지 확인했다(문서상 대조).

## 3. 제약과 결정

- 실행 환경과 확인 상태: Flutter 웹(Chrome)을 계획한 실행 환경으로 한다. 이 앱으로 실제 실행한 적은 없다(미확인).
- 시간·인원·사용할 기술: 학생 1명. 수업에서 배운 위젯(TextField, ListView, ChoiceChip 등 후보)과 StatefulWidget 상태 처리부터 사용한다. 새 패키지는 아래 결정의 저장용 1개만 후보로 둔다.
- 저장 위치와 유지 기간: 기기(브라우저) 로컬 저장. 앱·브라우저를 닫았다 열어도 유지하는 것이 목표. 브라우저 데이터 삭제 시 사라지는 것은 감수한다. 완료 항목을 얼마나 보관할지는 미정.
- 외부 서비스와 개인정보 범위: 계정·서버·유료 API를 사용하지 않는다. 기록은 기기 밖으로 보내지 않는다. 문서·테스트에는 "택배 반품 신청" 같은 가상 할 일만 쓰고 실제 이름·연락처·비밀번호는 넣지 않는다.
- 중요한 선택의 상황·선택지·결정·영향 (ADR-1 저장 방식):
  - 상황: 이 앱의 문제는 "잊어버림"이다. 다시 볼 때가 내일·주말이므로 기록이 앱 재시작 뒤에도 남아야 핵심 가치를 확인할 수 있다.
  - 선택지: ① 메모리 목록 ② 기기 로컬 저장(예: shared_preferences 패키지) ③ 서버 저장
  - 결정: ② 기기 로컬 저장 후보로 계획한다. ①은 재시작하면 사라져 가치 확인 불가, ③은 계정·서버 제외 제약 위반.
  - 영향: 패키지 1개 추가 검토가 필요하고, 저장 읽기 중 로딩·읽기 실패 상태와 AC가 새로 생긴다. 패키지 사용법은 구현 전에 공식 문서로 확인한다(아직 내용 미확인).
  - 재검토 조건: 패키지가 Flutter 웹에서 동작하지 않거나, 여러 기기 동기화 요구가 확정되면 다시 결정한다.
- 개발 규칙 세 가지와 각각의 확인 방법:
  1. 변수·함수 이름은 lowerCamelCase(예: showFrom, isDone) → Effective Dart: Style과 대조, `flutter analyze`
  2. 내용 검증 규칙(trim 후 빈 값 거절)과 시점 계산 규칙은 각각 한 함수에서만 처리 → 공백 입력·각 시점 선택을 실행해 결과 확인
  3. 코드 변경 뒤 `dart format lib`·`flutter analyze` 후 실제 실행으로 AC 확인 → 분석 성공만으로 AC 통과로 기록하지 않음

## 4. 화면·데이터·상태

- 핵심 흐름: [앱 열기] → [할 일 입력 + 다시 볼 때 선택 + 저장] → [그때가 되면 "지금 볼 것"에서 확인하고 완료 표시]
- 한 화면 안에 입력 영역, "지금 볼 것" 목록, "나중에" 목록을 둔다. 여러 화면으로 나누는 것은 필수가 아니다.

| 화면·영역 | 사용자 행동 | 바뀌는 값·다음 상태 |
| --- | --- | --- |
| 입력 영역 | 내용 입력, 다시 볼 때(오늘 저녁·내일·이번 주말) 선택, 저장 | 검증 통과 시 새 LaterItem 추가·기기 저장, 입력란 비움 / 실패 시 안내만 표시 |
| "지금 볼 것" 목록 | 확인, 완료 표시 | showFrom ≤ 현재 시각이고 isDone=false인 항목 표시 / 완료 선택 시 해당 id의 isDone=true |
| "나중에" 목록 | 확인 | showFrom > 현재 시각인 항목과 다시 볼 때를 표시 |
| 앱 시작 | 앱 열기 | 기기 저장소 읽기 중(로딩) → 성공(목록 또는 빈 안내) / 실패(오류 안내·다시 시도) |

| 데이터 필드 | 자료형 | 예시 | 규칙 |
| --- | --- | --- | --- |
| id | int | 1 | 항목마다 다름. 생성 방식(증가 숫자 등)은 구현 때 결정 |
| text | String | '택배 반품 신청' | trim() 후 빈 문자열이면 저장 거절. 최대 길이는 미정 |
| showFrom | DateTime | 2026-11-03 09:00 | 선택지에서 계산: 오늘 저녁=오늘 18:00, 내일=다음 날 09:00, 이번 주말=다음 토요일 09:00 (시각 값은 초안, 확정 전) |
| createdAt | DateTime | 2026-11-02 14:10 | 저장한 시각. 목록 정렬에 사용 |
| isDone | bool | false | 처음 false, 완료 표시 시 true |

자료형만으로 보장되지 않는 규칙: 빈 내용 거절, showFrom 계산, id 중복 방지는 상태 처리 코드에서 따로 지켜야 한다.

빈 상태·잘못된 입력·실패 안내 중 필요한 것:
- 빈 상태: 항목 0개 → "떠오른 일을 적어 두세요" 안내. "지금 볼 것"만 비었으면 "지금 할 일은 없어요" 안내.
- 잘못된 입력: 공백만 입력 → "할 일 내용을 입력하세요" 안내, 목록 변화 없음.
- 실패: 기기 저장소 읽기·쓰기 실패 → 오류 안내와 다시 시도 버튼. 빈 목록 안내와 구분한다.

| AC5 | 저장된 항목 0개로 앱 열기 | "떠오른 일을 적어 두세요" 안내 표시, 오류 안내는 보이지 않음 | 첫 화면 확인 | 미실행 |
| AC6 | 항목 1개 저장 → 브라우저 탭 새로고침(앱 재시작) | 같은 내용·다시 볼 때·완료 여부로 다시 표시 | 새로고침 전후 비교 | 미실행 |
| AC7 | 기기 저장소 읽기가 실패하는 상태로 앱 열기 | 오류 안내와 다시 시도 버튼 표시, 빈 목록 안내와 다르게 보임. 다시 시도 성공 시 목록 표시 | 실패를 만드는 방법 필요(실패하는 저장소 대역 등, 미정) | 미실행 |

계획을 작성한 상태와 앱 실행 결과를 구분합니다. 실제로 실행하기 전에는 통과로 바꾸지 않습니다.

## 6. 미정 질문

- 오늘 저녁·내일·이번 주말의 정확한 시각(18:00·09:00 등)은 확정 전 초안이다.
- "오늘 저녁"을 18:00 이후에 고르면 바로 "지금 볼 것"에 넣을지 확인이 필요하다(AC1은 바로 넣는 것으로 가정).
- 오늘이 토요일·일요일일 때 "이번 주말"이 오늘인지 다음 주 토요일인지 정해야 한다.
- 저장(쓰기) 실패 시 입력 내용을 입력란에 남길지. 현재 AC7은 읽기 실패만 다룬다.
- 내용 최대 길이, 완료 항목 보관 기간.
- AC7의 저장 실패를 어떤 방법으로 재현할지. (AC3는 now를 인자로 받는 계획으로 정함, 2026-11-02 검토)
